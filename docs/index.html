Aimo · open interface for purchasing agents

Agent interface

Aimo lets an external purchasing agent search a food-service wholesaler assortment, check allergens with evidence, get a fixed-price quote and order inside the authority it was granted. Everything else goes to a human for sign-off.

The interface is the Model Context Protocol over Streamable HTTP. The agent proposes; the same deterministic rules that guard the Aimo kitchen UI decide. No language model takes part in an allergen verdict, a price or an approval.

What is real and what is simulated. Catalog, price and availability come from the Valio Aimo Junction 2026 challenge data and its live mock API. Order submission is a local simulation: the mock has no order endpoint, so nothing is sent to Valio Aimo. Every order says so in its integration field.

Responses are framed as one server-sent event: an event: message line and a data: line with the JSON-RPC response. The MCP URL and the address of the signing key are shown in the Aimo UI and returned by GET /api/agent-info. The shared demo token is included there in open demo mode; when approvers are configured, only for a signed-in approver. The examples below use the shared demo token.

Initialize and call a tool with curl

export AIMO_URL=http://localhost:8787
export AIMO_TOKEN=<agent token>

# initialize
curl -s -X POST "$AIMO_URL/mcp" \
  -H "Authorization: Bearer $AIMO_TOKEN" \
  -H "Content-Type: application/json" \
  -H "Accept: application/json, text/event-stream" \
  -H "X-Agent-Name: menu-planner-agent" \
  -d '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-06-18","capabilities":{},"clientInfo":{"name":"curl","version":"1.0"}}}'

# tools/call: quote 1,000 L of lactose-free milk for Monday
curl -s -X POST "$AIMO_URL/mcp" \
  -H "Authorization: Bearer $AIMO_TOKEN" \
  -H "Content-Type: application/json" \
  -H "Accept: application/json, text/event-stream" \
  -H "X-Agent-Name: menu-planner-agent" \
  -d '{"jsonrpc":"2.0","id":2,"method":"tools/call","params":{"name":"prepare_order","arguments":{"delivery_date":"2026-11-16","requirements":["lactose_free"],"need":{"query":"laktoositon maitojuoma","amount":1000,"unit":"L"}}}}' \
  | sed -n 's/^data: //p'

Dietary requirements and verdicts

Supported: gluten_free, wheat_free, lactose_free, milk_free, egg_free, nut_free, soy_free, fish_free.

VerdictMeaningOrderable for that requirement
okVerified from supplier dataYes
failContains or may contain the allergenNo
unknownSupplier data is missing or contradicts itselfNo

Gluten-free is not wheat-free, and lactose-free is not milk-free. A product with a gluten-free claim may contain gluten-free wheat starch, which fails wheat_free. Lactose-free milk fails milk_free. Pass exactly the requirements the end consumer has.

get_authority, get_price_availability, list_orders, get_audit_log the remaining tools
  • get_authority takes no parameters. It returns per_order_limit_excl_vat, weekly_budget, spent_this_week, remaining_this_week, rules[] (each with effect: auto, human or never), supported_requirements and provenance.
  • get_price_availability takes product_ids (1–30) and delivery_date, both required. It always fetches fresh data. An unknown id comes back as { "product_id": "…", "error": "unknown_product" }.
  • list_orders returns order_id, status, title, created_by, delivery_date, total_excl_vat and approval_required for the 15 most recent orders from every source.
  • get_audit_log takes optional order_id and limit (1–100, default 30) and returns entries newest first: id, at, actor, action, text, orderId, hash.

Order lifecycle

One purchasing service, two transports. Aimo's kitchen assistant is the buyer's own agent; the wholesaler side provides the interface, deterministic rules and approval gate. Weekly orders, draft orders and chat quick orders use the same orders.ts: prepareQuote() and createOrder() functions as external agents: first a signed single-use quote, then an order from it. External agents use MCP; the kitchen assistant calls these functions in process, not through MCP or HTTP to itself.

Allergen, lot-size, credit and fresh supplier checks are shared. Kitchen orders keep the kitchen limit; external agents keep their own limits. Chat quick orders always need confirmation. With approvers configured, unsigned kitchen orders always wait for an approver. The rules, not a language model, decide.

1 · Quote

prepare_order returns a quote with fixed prices, a 15-minute expiry and a content hash. Lines that break a rule are refused here already. One quote, one order.

↓

2a · place_order

  • Fresh re-check of price, availability and allergens
  • Quote already used: quote_already_used, no second order
  • Rule broken: rejected_by_rules, no order
  • Price moved: price_changed, no order
  • Outside authority: approval_required, no order, audited
  • Otherwise: order created and approved by the rules

2b · request_approval

  • Fresh re-check
  • Quote already used: quote_already_used, no second order
  • Rule broken: rejected_by_rules, no order
  • Otherwise: order pending_approval, visible in the Aimo UI with the agent's name, note and every reason
↓

3 · Human decision (only after 2b)

Approve, reject or cancel in the Aimo UI. Approving runs another fresh re-check. If a rule is now broken the order stays pending_approval with recheck.ok = false. Agents cannot approve, reject or cancel.

↓

4 · Submitted (simulated)

The order is recorded locally with a confirmation SIM-XXXXXXXX. Nothing is sent to Valio Aimo.

Quotes and idempotency

  • Fixed price for automatic orders. A quote fixes lines, quantities and unit prices as observed when it was prepared. Both automatic kitchen orders and place_order refuse with price_changed if a live unit price differs by more than EUR 0.005. No order is created; prepare a new quote.
  • Expiry. 15 minutes (expires_at). An expired or unknown quote returns rejected_by_rules.
  • Single use. A quote produces at most one order. After that, any call with another idempotency key returns quote_already_used with order_id and order_status. The quote stays used when the order is rejected or cancelled: prepare a new quote. A refused place_order created no order and leaves the quote usable.
  • Content hash. content_sha256 is the SHA-256 of the stored quote content: agent name, request, delivery date, lines, totals and shortfall. It identifies exactly what was quoted. The server does not ask for it back.
  • Approval path unchanged. request_approval, over-limit kitchen orders and mandatory chat confirmations do not refuse on a price difference. The pending order uses fresh prices. Human approval re-checks and submits at the price checked at that moment; changes are recorded in the order events and the final total in the audit. The approval click currently sends at a changed price without a second preview. The signed confirmation contains final prices, and the UI proof view shows differences from the original quote.
  • Idempotency key. Required for place_order and request_approval, at least 8 characters. Reuse it on every retry: a key that already has an order returns that order with duplicate: true.
  • Refused attempts leave no order. The key of a refused place_order can be used for the following request_approval.
  • Never twice. Approving an already submitted order does nothing.
  • Scope. Quotes belong to an account and recipient. Kitchen quotes have a separate owner (source: ui, signed recipient id: kitchen, identity: kitchen, name Aimo). Neither shared-demo nor registered-agent MCP credentials can use them, nor can the kitchen consume an MCP quote. A registered agent's keys are its own. Quotes and keys made with the shared demo token are shared only by its users.
  • Kitchen retries. Existing content-based keys (delivery date, products and quantities) are checked before preparing a quote. Sequential or concurrent retries return the earlier order, with no surplus quote. Rejected or cancelled kitchen orders need a fresh quote.

A registered agent's weekly limit counts what it ordered on its own authority in the last 7 days; orders a person approved do not use it up. The check runs at the quote and inside shared order creation immediately before automatic submission, or again at human approval. Unstated stock quantities are notes for both sources, not approval reasons; some historical examples above predate this behaviour. Creating, changing and revoking an agent is written to the audit log with the person's name.

The live values and rule texts are in get_authority. Approval cannot override a "never" rule: the approver's click triggers the same checks again.

Partial availability and substitution

Aimo never substitutes silently.

Named options and supplier evidence

For unambiguous needs, ranked_options shows up to three role winners: cheapest (whole-pack covering cost), most_reliable (highest available delivery history), most_sustainable (the rule below). A product winning several roles appears once, with a roles array of { role, label }. No supporting data means no role. Ambiguous needs still show up to five verified choices, without endorsements. Automatic allocation is unchanged: cheapest first, with availability-capped splits. Select another product with need.product_id or items.

Each option has structured basis: cost_to_cover_eur_excl_vat, rounded sales_units, covered_amount, delivery_reliability_history, packaging-label ids, country_of_origin, and co2_kg_per_kg_category_average. Missing data is null. Notes show partial availability: a full covering price is hypothetical when stock is insufficient. Product descriptions include packaging_labels (ids and localized names), country_of_origin and packaging_label_note. Temperature markers are excluded; untranslated labels remain visible by id. These are supplier declarations, and Aimo does not verify certificates.

Sustainability rule: require a known environmental/responsibility label: EU organic, Nordic Swan, Rainforest Alliance, EU Ecolabel, MSC, Fairtrade, ASC, KRAV, Finnish organic Sun, Soil Association, UTZ or Dolphin Safe. Multiple labels earn no extra points. Prefer declared Finnish origin among these as a local-sourcing choice, not evidence of lower transport emissions. Use lower category-average CO₂ only when all remaining candidates share one category and all have a value; otherwise do not use CO₂ for ranking. Remaining ties follow the covering-cost order. The winner carries the localized rule in basis.sustainability_rule. Health/origin marks (Heart Symbol, Food from Finland, Key Flag) and unrecognised labels are shown but not counted as environmental evidence. Missing evidence does not prove another product worse. CO₂ is per kg, not a measured SKU footprint or a calculated total for litres. This is not a life-cycle assessment and does not estimate waste; a larger pack with more excess may win, with amount and cost shown.

Declare replacement intent

Set optional substitute_for on an item or need to name the product being replaced. It must exist and differ from the selected product; a merged line cannot have conflicting source ids (invalid_request). All normal checks still apply. A new replacement gets substitution: true and a human-approval reason; place_order refuses with approval_required, then request_approval sends it to a person.

The account has accepted the replacement product if it is in its approved overrides/swaps or any previously submitted order. After human approval and submission, a fresh quote needs no repeated substitution approval; other limits still apply. Acceptance is per product and account, not per pair. No parallel memory is stored. The quote keeps its original flag. Quote/order lines retain substitute_for; the order also shows substitution_note, including after price-change re-approval. The signed-document schema is unchanged. Kitchen replacements already require a human click and use existing memory; a recipe's own special-diet product is not a replacement.

Limit: if an agent omits substitute_for, it simply orders that product within its authority. The rule cannot detect an undeclared substitution. Need splitting alone does not activate the rule.

  • Explicit items. Exactly these products are quoted. If the stated availability is lower than the quantity, the quote is refused: "…: only 19 available, order has 5000."
  • Lot sizes. order_multiple on products and quote lines is the step the supplier's lot size allows (1 for most products; a lot of 0.01 means 1; a fractional lot such as 1.5 is read cautiously as 3, 6, 9 …). A need is rounded up to the next allowed quantity, and the line's why says so. An item off the lot is refused: "…: sold in lots of 2 sales units, so a quantity of 3 is not allowed. The nearest allowed quantities are 2 and 4."
  • A need. All usable name matches are checked before relevance restriction. Whole name words are preferred, but do not prove that a word is the head noun rather than a flavour. Different categories mean different types, except reviewed equivalences for explicit jauhoseos (21310/21320/21370) and olut (84966/85001/21405). More than one type or unrequested alcohol-free, decaffeinated or pre-cooked wording requires a choice. There is no dominant-category shortcut.
  • Covering cost. Verified, orderable options are ranked by the total cost of covering the amount in whole sales units and allowed lots, not €/kg or €/L. Ties prefer smaller packs, then historical reliability. Allocation is capped by availability and reranked for the remainder, across at most three products. This is greedy, not globally optimal mixed-pack optimisation. Every line says why it is there.
  • Several needs. Each entry is reported in fulfilment_by_need. A missing need is not_found; an ambiguous one is selection_required, with selection_reason and verified ranked_options. Both add no line and do not stop the others. Ambiguity is measured before unsafe products are removed, so a missing declaration cannot turn a flavour into the intended ingredient. Choose explicit items, need.product_id or a more precise query.
  • Shortfall. fulfilment reports requested, covered, shortfall and split_across_products. If the need cannot be covered, the quote is issued for the covered part and the agent decides.
  • One product only. With need.product_id the shortfall is reported and not filled. Up to three verified substitute_options are informational only: supplier pairs first, then same category, then other verified query matches, by covering cost within each tier. Each must cover the shortfall alone. Each carries tier (supplier_substitute, same_category, other_verified), tier_label, basis.sales_units and the pinned substitute_for for a new request. These appear in fulfilment_by_need, also at the top level for one need; no-quote errors retain them per need. Nothing is silently added. Supplier pairs do not guarantee recipe/flavour equivalence. Real example: 300 kg requested, 77 sacks of 3 kg available, covered: 231, shortfall: 69.
  • What was ruled out. excluded_by_rules counts products dropped as failed or unknown and gives up to three examples with the reason. If no lines are allocated, the error is selection_required when any need needs a choice, otherwise no_suitable_product. Both retain fulfilment_by_need and create no quote.

Signed quotes and order confirmations

An agent does not have to take a price or a confirmation on trust. The server signs both with its own key, with open standards only. The same signatures are retained on kitchen and external-agent orders, independently of quote cleanup.

Evidence in the UI. An expandable row on each order card shows the quote id, issuer, recipient, account, price/availability observation time, validity and signed confirmation. The browser verifies the signatures itself with WebCrypto Ed25519 and the same-origin /.well-known/jwks.json. Unsupported browsers, unavailable keys and failed verification are explicitly labelled, never marked verified. Signed content and JWS can be viewed and copied. Differing quoted and submitted unit prices and totals are shown directly; if either signature is not verified, the comparison is explicitly labelled unverified. Signature validity is separate from quote expiry and single-use status. Old state files still load: legacy orders without retained quote evidence say that no quote is available.

  • FormatJWS compact serialization (RFC 7515) with JWT claim names (RFC 7519)
  • AlgorithmEdDSA with Ed25519 (RFC 8037)
  • Public keyJWK Set (RFC 7517) at GET /.well-known/jwks.json; the key id is the JWK thumbprint (RFC 7638)
  • Signed quoteprepare_order.signed_quote: issuer, agent and whether its identity is registered, account, quote id, expiry, delivery date, lines (product, GTIN, quantity, unit price), totals, and when price and availability were fetched
  • Signed confirmationorder.signed_confirmation once an order is submitted: order id, confirmation number, quote id, lines, totals, who approved, and "submission": "local_simulation"

To verify: fetch the JWK Set from the host you connected to, require alg to be EdDSA, take the key with the header's kid, verify the signature over <header>.<payload>, then compare the payload with the plain answer.

import { createPublicKey, verify } from 'node:crypto';

const { keys } = await (await fetch('https://<your-aimo-host>/.well-known/jwks.json')).json();
const [h, p, sig] = signedQuote.split('.');
const header = JSON.parse(Buffer.from(h, 'base64url'));
const jwk = keys.find(k => k.kid === header.kid);
const ok = header.alg === 'EdDSA' && !!jwk
  && verify(null, Buffer.from(`${h}.${p}`), createPublicKey({ key: jwk, format: 'jwk' }), Buffer.from(sig, 'base64url'));

What the signature proves, and what it does not. It proves that this Aimo server issued exactly this content and that nobody changed it afterwards. It does not prove that the price and availability are right: they come from the Valio Aimo challenge mock API, which does not sign its answers. It does not prove that an order reached a supplier: submission is a local simulation, and the signed confirmation says so. The key is not certified by a third party and is not rotated yet.

Human approvers

  • Open demo mode (default). No approvers are configured. Anyone who can open the Aimo UI can approve, and the log records "Kitchen manager". The UI and GET /api/state (integration.access) say so.
  • With approvers (APPROVERS, names and PINs). Approving, rejecting and cancelling an order, registering, changing and revoking an agent, changing the credit limit and resetting the demo need a signed-in approver. The UI asks for name and PIN when such an action is tried and then carries on. The approver's name goes into the audit log, the order and the signed confirmation. Everyday use stays open; an order nobody signed in for waits for an approver.
  • PINs are not stored or logged, are compared in constant time, and five wrong ones lock the name for 15 minutes.

Audit chain

Every action that matters is appended to one log with its actor: the kitchen manager or the signed-in approver by name, Aimo, Aimo rules, Registered agent (<name>), or External agent (<name>) for the shared demo token. Each entry stores

hash = SHA-256( previous_hash + JSON(entry) )      first previous_hash = "genesis"

so changing or removing an earlier entry breaks every later hash. Agents read the log with get_audit_log. A real entry:

{ "id": "a16", "at": "2026-11-14T18:15:46.983Z", "actor": "Kitchen manager",
  "action": "order_approved", "text": "Order AIMO-2026-0002 approved (€1,010.00).",
  "orderId": "AIMO-2026-0002", "hash": "5765184681a524f3" }

The chain is tamper-evident for whoever holds the state file. It is not anchored outside the application, and the API shows hashes truncated to 16 hex characters, so an agent can reference entries but cannot recompute the chain from API output alone.

Known limitations

  • The shared demo token is still accepted. Its users share one credential, pick any account and declare their own name. It is marked self_declared everywhere, but it is not switched off.
  • Agent tokens are bearer tokens: whoever holds one can use it until it expires or is revoked.
  • Signatures cover Aimo's commitment, not the supplier's data. One signing key, no rotation, no third-party certification.
  • Approvers are a name and a PIN from server configuration, not accounts with roles. Without APPROVERS the UI is open.
  • Fractional lot sizes are read cautiously (whole sales units that are a multiple of the lot). This is our assumption, not a confirmed supplier rule.
  • The 429 behaviour is not verified against the live mock. Aimo paces its calls to 5 per second and waits out a cooldown after a 429, following Valio Aimo's description; 30 s is assumed when no Retry-After is sent.
  • Conservative matching. Whole words, categories and a small set of variant markers are heuristics, not semantic understanding. Broad queries may need selection unnecessarily; same-category flavours and catalog errors can still escape detection. Explicit items avoid automatic interpretation.
  • Replacement intent must be declared. The substitution rule requires substitute_for; undeclared changes are not detectable. Acceptance is per product/account, not pair-specific. Ordinary need splits are reported but do not themselves need substitution approval.
  • "Spent this week" is the sum of all submitted orders in the kitchen's state, not a calendar-week window.
  • Mock snapshot. The challenge availability data is fixed. Some cutoffs in it are already in the past, which by default forces human approval.
  • Simulated submission. A submitted order has not reached any supplier.
